## 1. Executive Summary

### 워크허브가 해결하는 문제

금융업 현장의 업무 시스템은 여전히 **정형 데이터 중심**이다. CRM에 고객명과 연락처를 입력하고, ERP에 거래 금액을 기록하고, 엑셀로 리포트를 만든다. 그러나 실제 의사결정에 필요한 정보의 80%는 **비정형 데이터**에 흩어져 있다.

- Slack에서 오고 간 고객 대화
- 미팅 후 메모나 음성 녹취
- 이메일 스레드에 묻힌 합의 내용
- 팀 내부 문서와 보고서 초안
- 규제 변화에 대한 산발적인 논의

기존 시스템은 이 비정형 데이터를 다루지 못한다. 담당자가 바뀌면 맥락이 사라지고, 주간 리포트를 쓰려면 여러 시스템을 뒤져야 하며, "이 고객과 지난달에 무슨 얘기를 했지?"라는 단순한 질문에도 30분이 걸린다.

**워크허브는 이 문제를 근본적으로 다르게 접근한다.**

### 핵심 접근: 컨텍스트 + AI 에이전트

워크허브는 데이터를 테이블의 행(Row)이 아니라 **컨텍스트(Context)**로 다룬다.

| 기존 시스템 | 워크허브 |
|------------|---------|
| 고객 정보 = DB 레코드 | 고객 정보 = 대화, 미팅, 거래, 피드백을 종합한 **컨텍스트** |
| 검색 = SQL 쿼리 | 검색 = AI 에이전트에게 자연어 질문 |
| 리포트 = 수동 작성 | 리포트 = AI가 컨텍스트 기반 자동 생성 |
| 인사이트 = 대시보드 숫자 해석 | 인사이트 = AI가 패턴 감지 후 **선제적 알림** |

각 허브(SalesHub, FinHub, OnboardingHub, StrategyHub)는 현업의 업무 흐름에 맞춘 **전문 AI 에이전트**를 보유한다. SalesHub의 "Reno"는 고객 미팅 전 브리핑을 자동 생성하고, FinHub는 거래 라이프사이클을 관리하며, OnboardingHub는 KYC 서류를 OCR로 자동 인식한다. StrategyHub는 산업·규제 동향을 자동 수집하고 AI 기반 문서 생성·리뷰 환경을 제공한다.

이 에이전트들은 중앙 **Context Pool**에 축적된 컨텍스트를 활용하므로, 시간이 지날수록 더 정확하고 유용해진다.

## 2. 워크허브란 무엇인가

### 기존 업무시스템의 한계: 정형 데이터의 사각지대

금융업에서 사용하는 기존 업무 도구들 — Salesforce, HubSpot, SAP, 사내 ERP — 은 모두 **정형 데이터베이스(RDB)** 위에 구축되어 있다. 고객 테이블, 거래 테이블, 활동 테이블에 행(Row)을 추가하는 방식이다.

이 구조의 근본적 한계는 세 가지다:

**1) 비정형 데이터를 담을 수 없다**

"지난 미팅에서 A사 CFO가 내년 예산 확대 가능성을 언급했다"는 정보는 CRM의 어떤 필드에도 들어가지 않는다. 미팅 메모를 첨부할 수는 있지만, 시스템이 그 내용을 이해하거나 활용하지는 못한다. 결국 담당자의 기억에만 의존하게 된다.

**2) 맥락(Context)이 유실된다**

고객과의 관계는 단일 레코드가 아니라 수개월에 걸친 대화, 미팅, 이메일, 내부 논의의 **축적**이다. 담당자가 교체되면 이 맥락이 통째로 사라진다. 새 담당자는 CRM의 기본 정보만으로 관계를 이어가야 하며, 이전 담당자가 쌓은 신뢰와 이해의 깊이를 복원할 수 없다.

**3) 인사이트가 사후적이다**

기존 대시보드는 "이미 일어난 일"을 보여준다. 이번 달 매출, 지난 분기 거래 건수, 올해 고객 이탈률. 하지만 의사결정자가 정말 필요한 것은 "앞으로 일어날 일" — 위험 신호, 기회 포착, 트렌드 변화 — 에 대한 선제적 알림이다.

### 워크허브의 접근: "컨텍스트 중심 AI 업무 플랫폼"

워크허브는 데이터를 RDB의 행이 아니라 **컨텍스트**라는 단위로 다룬다.

**컨텍스트**란 특정 주제(고객, 거래, 프로젝트)에 대한 모든 관련 정보 — 대화, 미팅, 문서, 거래 내역, 외부 동향 — 를 AI가 자동으로 종합하고 요약한 것이다. 정형/비정형을 가리지 않고 모든 소스에서 정보를 수집하며, 시간이 지남에 따라 자동으로 갱신된다.

이 컨텍스트 위에서 AI 에이전트가 동작한다. 에이전트는 사용자의 질문에 답하고, 브리핑을 생성하고, 위험을 감지하고, 리포트를 작성한다. 에이전트가 활용할 수 있는 컨텍스트가 풍부할수록 결과물의 품질이 높아지며, 이것이 워크허브의 핵심 선순환 구조다.

### 핵심 차별점 3가지

| # | 차별점 | 설명 |
|---|--------|------|
| 1 | **Context Pool** | 비정형 데이터를 포함한 모든 업무 정보를 자동 수집·정제·축적하는 중앙 지식 저수지 |
| 2 | **AI 에이전트** | 허브별 전문 에이전트가 Context Pool을 활용하여 브리핑, 분석, 리포트를 자동 생성 |
| 3 | **멀티 파이프라인 입력** | Slack, 음성, OCR, 이메일, 웹 수집 등 8가지 자동 수집 경로로 Context Pool을 지속 확충 |

## 4. 시스템 전체 구조

### 허브 생태계

워크허브는 **중앙 관리 허브(HubManager)** + **5개 업무 허브**(SalesHub, FinHub, OnboardingHub, StrategyHub)로 구성된 생태계이다.

| 허브 | 역할 | 주요 사용자 | AI 에이전트 |
|------|------|-----------|------------|
| **HubManager** | SSO 인증, 권한 관리, AI 페르소나 중앙 관리, 모니터링 | 어드민 | 페르소나 관리 AI |
| **SalesHub** | 고객 관리(CRM), 미팅, 거래 추적, 주간 리포트 | 세일즈, BD | Reno AI |
| **FinHub** | 거래(Deal) 관리, 암호자산 거래, 승인 워크플로우 | 재무 | 거래 분석 AI |
| **OnboardingHub** | 신규 고객 온보딩, KYC/AML, 서류 검토 | 운영팀, 컴플라이언스 | OCR AI |
| **StrategyHub** | 전략 문서 생성, 협업 리뷰, 정보 수집, 규제 관리 | 전략기획, C레벨 | 문서 편집 AI |

                    │   HubManager    │
                    │  (SSO Gateway)  │
                    │                 │
                    │  JWT 쿠키 발급   │

                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┬──────────────┐
              ▼              ▼              ▼              ▼
        ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
        │ SalesHub │  │  FinHub  │  │Onboarding│  │ Strategy │
        │          │  │          │  │   Hub    │  │   Hub    │
        │ 독립 DB  │  │ 독립 DB  │  │ 독립 DB  │  │ 독립 DB  │
        │ 독립 API │  │ 독립 API │  │ 독립 API │  │ 독립 API │

- 사용자는 HubManager에서 **한 번 로그인**하면 모든 허브에 접근 가능 (쿠키 기반 SSO)
- 각 허브는 **독립적인 데이터베이스와 API**를 보유하여 서로 영향을 주지 않음
- HubManager가 **중앙 계정·권한·AI 페르소나**를 관리하여 일관성 유지

## 5. AI 엔진 아키텍처

### 컨텍스트 + AI 에이전트 모델 vs 전통 RDB 모델

```
┌─ 전통 RDB 모델 ─────────────────┐    ┌─ 워크허브 모델 ─────────────────┐
│                                   │    │                                   │
│  사용자 → SQL 쿼리 → DB → 결과    │    │  사용자 → 자연어 → AI → 인사이트  │
│                                   │    │              ↑                    │
│  · 정형 데이터만 처리              │    │         Context Pool              │
│  · 검색어를 정확히 알아야 함       │    │  · 정형 + 비정형 통합            │
│  · 사후적 대시보드                 │    │  · "A사 최근 상황 알려줘"        │
│  · 수동 리포트 작성                │    │  · 선제적 알림 + 자동 리포트      │
│                                   │    │                                   │
└───────────────────────────────────┘    └───────────────────────────────────┘
```

### LLM 멀티 프로바이더 전략

워크허브는 단일 LLM에 의존하지 않고, 멀티 프로바이더 전략으로 안정성과 비용 효율을 확보한다.

| 우선순위 | 프로바이더 | 용도 | 월 예산 |
|---------|-----------|------|--------|
| 1순위 | Claude (Anthropic) | 주력 모델 — 문서 생성, 분석, 대화 | 무제한 |
| 2순위 | GPT-4o (OpenAI) | 보조 — 특정 작업 최적화 | $100/월 |
| 3순위 | Gemini (Google) | 폴백 — 2순위 예산 초과 시 | $100/월 |

**자동 폴백 구조**: 2순위/3순위 월 예산 초과 시 자동으로 1순위(Claude)로 전환. 서비스 중단 없음.

### 페르소나(Persona) 시스템

각 AI 에이전트는 **페르소나**라는 성격과 역할 정의를 갖는다. 페르소나는 HubManager에서 중앙 관리되며, 허브별로 전문화된 에이전트를 구성한다.

| 페르소나 | 소속 허브 | 역할 | 톤 |
|---------|----------|------|-----|
| **Reno** (내부) | SalesHub | 영업팀 AI 어시스턴트 — 고객 분석, 미팅 준비, 메시지 작성 | 친근, 반말 |
| **Reno** (외부) | SalesHub | 고객 대면 AI — 격식 있는 응대 | 경어, 격식 |
| **문서 편집 AI** | StrategyHub | 문서 리뷰 반영, 톤 조정, 품질 검증 | 비즈니스 격식체 |

## 6. Context Pool 아키텍처

### 비정형 데이터 수집 → 정제 → 컨텍스트화

Context Pool(컨텍스트 풀)은 워크허브 생태계의 **지식 저수지**이다. 다양한 소스에서 흘러들어온 비정형 데이터가 AI에 의해 정제·분류되어 **고객별/거래별/조직별 컨텍스트**로 구조화된다.

```
  ┌─────────────────────────────────────────────────┐
  │              Context Pool 파이프라인               │
  │                                                   │
  │  [ 수집 ]         [ 정제 ]         [ 컨텍스트 ]   │
  │                                                   │
  │  Slack ──┐                         ┌─ 고객 A 컨텍스트
  │  음성 ───┤     ┌───────────┐      ├─ 고객 B 컨텍스트
  │  OCR ────┤     │ AI 정제/  │      ├─ 거래 X 컨텍스트
  │  수동 ───┼────→│ 분류 엔진 │─────→├─ 프로젝트 Y 컨텍스트
  │  이메일 ─┤     │           │      ├─ 산업 동향 컨텍스트
  │  API ────┤     └───────────┘      └─ 규제 변화 컨텍스트
  │  크론 ───┤                                        │
  │  Collector┘                                       │
  │                                                   │
  └─────────────────────────────────────────────────┘
```

### 8가지 입력 파이프라인

| # | 파이프라인 | 소스 | 컨텍스트 유형 | 자동화 수준 |
|---|----------|------|-------------|-----------|
| 1 | **Slack 메시지** | 채널 모니터링, @멘션 | 고객 동향, 내부 논의 | 완전 자동 |
| 2 | **음성 녹취** | Fireflies 연동 | 미팅 요약, 핵심 합의 | 완전 자동 |
| 3 | **문서 OCR** | GCP Vision | KYC 서류, 사업자등록증 | 완전 자동 |
| 4 | **수동 입력** | 웹 UI 직접 입력 | 미팅 노트, 메모 | 수동 |
| 5 | **이메일** | 이메일 연동 (계획) | 커뮤니케이션 로그 | 반자동 |
| 6 | **외부 API** | 시장 데이터, 규제 정보 | 산업/규제 동향 | 완전 자동 |
| 7 | **크론 배치** | 정기 집계/요약 | 주간 통계, 건강도 | 완전 자동 |
| 8 | **Collector** | RSS, 웹 스크래핑, PDF | 규제/산업 뉴스 | 완전 자동 |

### 컨텍스트 저장소 구조

컨텍스트는 세 가지 차원으로 조직된다:

- **고객별 컨텍스트**: A사와의 모든 상호작용 — 대화, 미팅, 거래, 피드백
- **거래별 컨텍스트**: 특정 딜의 진행 경과, 관련 문서, 승인 이력
- **조직별 컨텍스트**: 산업 동향, 규제 변화, 내부 전략 문서

각 컨텍스트는 AI가 주기적으로 자동 요약하며, 새 정보가 유입될 때마다 갱신된다. 시간이 지날수록 풍부해지는 **자기 강화(Self-Reinforcing)** 구조이다.

## 7. HubManager — 중앙 관리 허브

### 7.1 허브 개요 및 포지셔닝

HubManager는 워크허브 생태계의 **관제탑**이다. 직접적인 비즈니스 기능은 수행하지 않지만, 모든 허브가 작동하기 위한 핵심 인프라 — 인증, 권한, AI 페르소나, 모니터링 — 를 제공한다.

```
                    ┌─────────────────┐
                    │   HubManager    │
                    │                 │
                    │  · SSO 인증     │
                    │  · 권한 관리    │
                    │  · AI 페르소나  │
                    │  · LLM 모니터링 │
                    │  · 푸시 알림    │
                    │  · 문서 관리    │
                    └────────┬────────┘
                             │
              ┌──────┬───────┼───────┬──────┐
              ▼      ▼       ▼       ▼      ▼
          SalesHub FinHub OnboardingHub StrategyHub
```

**다른 허브와의 관계**: 모든 허브는 HubManager의 SSO 토큰으로 인증하며, AI 에이전트는 HubManager에 등록된 페르소나 정의를 사용한다. LLM 사용량과 비용은 HubManager 어드민 대시보드에서 통합 모니터링된다.

### 7.2 통합 계정 및 권한 관리

**5단계 역할 체계**

| 역할 | 권한 범위 | 대상 |
|------|----------|------|
| **MASTER** | 전체 시스템 관리, 모든 권한 | 시스템 관리자 |
| **ADMIN** | 허브별 관리, 사용자 초대 | 허브 책임자 |
| **USER** | 업무 기능 사용, 데이터 입력/수정 | 일반 실무자 |
| **VIEWER** | 읽기 전용 접근 | 리포트 열람자 |
| **GUEST** | 제한된 기능 접근 | 외부 협력사 |

**허브별 멤버십 관리**

사용자는 허브마다 다른 역할을 가질 수 있다. 예를 들어, Peter는 SalesHub에서는 ADMIN이지만 FinHub에서는 USER일 수 있다. 이 멀티 허브 권한 구조는 `hub_memberships` 테이블로 관리된다.

**SSO 인증 흐름**

```
사용자 ──→ HubManager 로그인 ──→ JWT 쿠키 발급 (.workhub.biz)
                                         │
                                         ▼
                                  쿠키가 모든 허브에서 유효
                                  (SalesHub, FinHub, ...)
                                         │
                                         ▼
                                  각 허브가 JWT 검증 후 접근 허용
```

**계정 워크플로우**: 생성 → 허브 초대 → 역할 배정 → 활성 → (필요시) 비활성화

### 7.3 AI 페르소나 중앙 관리

HubManager는 워크허브 생태계의 모든 AI 에이전트 페르소나를 **중앙에서 관리**한다.

**페르소나 정의 구조**

각 페르소나는 다음 속성을 갖는다:

- **이름**: Reno, 문서편집AI 등
- **역할 설명**: 이 에이전트가 수행하는 업무 정의
- **톤/스타일**: 격식체/반말, 이모지 허용 여부
- **도구(Tools)**: 에이전트가 사용할 수 있는 기능 목록
- **지식 범위**: 접근 가능한 Context Pool 영역
- **변형(Variant)**: 내부용/외부용 등 상황별 다른 성격

**버전 관리**: 페르소나 정의를 변경할 때마다 변경 이력이 자동 기록된다. 문제 발생 시 이전 버전으로 즉시 롤백 가능하다.

**런타임 로드 순서**: Cache → DB → YAML. 성능을 위해 캐시를 우선 참조하되, 최신 정의는 DB에 저장하고, 초기 시드 데이터는 YAML 파일로 관리한다.

### 7.4 통합 어드민 대시보드

어드민 대시보드는 전체 워크허브 생태계의 **운영 현황을 한눈에** 파악할 수 있는 통합 관리 화면이다.

**허브별 사용 현황**: 각 허브의 활성 사용자 수, 최근 활동, 주요 지표

**LLM 사용량/비용 통계**:
- 프로바이더별 (Claude/OpenAI/Gemini) 토큰 사용량 및 비용
- 허브별 AI 사용 현황
- 목적별 분류 (브리핑, 리포트, 분석, 문서 생성 등)
- 월간 비용 추이 및 예산 대비 현황

**AI 대화 로그 관리**: 에이전트별 대화 이력 조회, 품질 검토, 문제 대화 플래그

**배너/공지사항 관리**: 전체 허브 또는 특정 허브에 공지사항 배포

### 7.5 푸시 알림 시스템

Firebase Cloud Messaging(FCM) 기반의 통합 알림 시스템으로, 웹과 모바일 환경에서 동일한 알림을 수신한다.

**알림 유형**:
- **긴급 알림**: 위험 거래 감지, KYC 서류 만료 임박
- **업무 알림**: 미팅 브리핑 준비 완료, 리포트 생성 완료
- **정보 알림**: 주간 리포트 발행, 새 문서 공개

**허브별 알림 라우팅**: 각 허브에서 발생한 이벤트가 해당 허브의 구독자에게만 전달되며, 사용자별 알림 선호도 설정이 가능하다.

### 7.6 문서 및 기술 자료 관리

내부 기술 문서, 운영 가이드, 정책 문서를 중앙에서 관리하는 저장소이다.

**태그 기반 분류**: 문서에 태그를 부여하여 주제별, 허브별, 유형별 검색이 가능하다.

**허브간 공유 문서**: 특정 문서를 여러 허브에서 참조할 수 있도록 공유 설정을 지원한다.

## 8. SalesHub — 영업 CRM + AI 어시스턴트

### 8.1 허브 개요 및 포지셔닝

SalesHub는 **고객 관계의 모든 맥락을 AI로 관리**하는 허브이다. 단순한 CRM(고객 관계 관리)을 넘어, AI 에이전트 Reno가 고객 컨텍스트를 자동으로 축적하고, 미팅 준비부터 팔로업까지 영업 실무의 전 과정을 지원한다.

**세일즈/BD 실무자의 하루 — 워크허브 이전 vs 이후**

| 시간 | 이전 | 이후 (워크허브) |
|------|------|---------------|
| 09:00 | CRM 열고 오늘 미팅 고객 수동 조사 (30분) | Reno가 미팅 브리핑 자동 생성 완료, Slack DM으로 수신 |
| 10:00 | 미팅 진행 | 미팅 진행 (동일) |
| 11:00 | 미팅 메모 정리, CRM에 수동 입력 (20분) | 음성 녹취 자동 전사, Reno가 미팅 요약 + 컨텍스트 갱신 |
| 14:00 | 팔로업 이메일 작성 (15분) | Reno가 초안 생성, 톤 선택 후 발송 |
| 16:00 | Slack 대화에서 고객 언급 수동 확인 | Reno가 채널 모니터링 후 관련 고객 컨텍스트 자동 업데이트 |
| 17:00 | — | 위험 고객 알림 수신: "B사 30일간 미응답, 건강도 Critical" |

### 8.2 고객(Customer) 관리

**고객 프로필 구조**

각 고객은 기본 정보 외에 다음을 포함한다:
- **카테고리**: 기관투자자, 법인, 개인, 파트너 등
- **태그**: 자유 형식의 분류 태그
- **담당자**: 세일즈/BD 담당자 배정
- **건강도 배지**: AI가 실시간 산출하는 관계 건강도 (Healthy/Warning/Critical)

**고객 상세 페이지**

고객 상세 페이지는 다음 탭으로 구성된다:
1. **컨텍스트**: AI가 종합한 고객과의 전체 맥락 요약
2. **미팅**: 예정/완료 미팅 목록, 미팅 노트
3. **활동 타임라인**: 고객 관련 모든 활동의 시간순 기록
4. **거래**: 진행 중/완료 거래 내역

**고객 목록 뷰**

- 카테고리별, 담당자별 필터링
- 건강도 배지 컬럼 (Healthy/Warning/Critical)
- 최근 활동일 기준 정렬

**데이터 입력 경로**

| 경로 | 설명 | 자동화 |
|------|------|--------|
| 수동 입력 | 웹 UI에서 직접 고객 정보 등록 | 수동 |
| Slack | 채널 모니터링으로 고객명 자동 추출 | 자동 |
| 음성 녹취 | Fireflies 연동으로 미팅 후 자동 반영 | 자동 |
| CSV 임포트 | 기존 고객 데이터 대량 등록 | 반자동 |

### 8.3 고객 컨텍스트 자동 관리

**컨텍스트란?**

고객 컨텍스트는 특정 고객과의 **모든 상호작용을 AI가 종합·요약한 살아있는 문서**이다. CRM의 정적 필드가 아니라, Slack 대화, 미팅 노트, 음성 녹취, 이메일 등 다양한 소스에서 자동으로 수집되어 지속적으로 갱신된다.

**자동 수집 소스**

```
  Slack 채널 ───┐
  미팅 노트 ────┼──→ AI 정제 ──→ 고객 컨텍스트 (Markdown + JSONB)
  음성 녹취 ────┤                     │
  이메일 ───────┘                     ▼
                              최근 활동 10건 요약
                              핵심 합의 사항
                              주요 리스크
                              다음 액션 아이템
```

**AI 자동 요약 및 갱신 주기**: 새 정보가 유입될 때마다 AI가 컨텍스트를 갱신하며, 크론 배치로 일 1회 전체 재요약을 수행한다.

**활용 시나리오**:
- **미팅 전**: 고객 히스토리 빠른 파악
- **주간 리포트**: 고객별 주요 동향 자동 포함
- **담당자 핸드오버**: 새 담당자가 즉시 맥락 파악 가능

### 8.4 Reno AI — 미팅 브리핑 생성기

Reno AI의 핵심 기능 중 하나로, **미팅 전 자동 브리핑을 생성**한다.

**브리핑 포함 내용**:
1. **고객 요약**: 기본 정보, 카테고리, 현재 관계 상태
2. **최근 활동 10건**: 시간순 정리 (미팅, Slack 대화, 거래 등)
3. **핵심 히스토리**: AI가 추출한 주요 합의/이슈
4. **제안 주제**: 이번 미팅에서 다뤄야 할 주제 AI 추천
5. **주의 사항**: 미해결 이슈, 약속된 사항 리마인드

**자동 생성 트리거**: 미팅 24시간 전 크론이 자동으로 브리핑 생성. 담당자에게 Slack DM 또는 푸시 알림으로 통보.

**사용자 편집**: 생성된 브리핑은 AI 초안이며, 담당자가 직접 수정·보완할 수 있다.

### 8.5 Reno AI — 메시지 드래프터

미팅 후 팔로업 이메일이나 Slack 메시지의 **초안을 자동 작성**한다.

**톤 선택**:
| 톤 | 용도 | 예시 |
|----|------|------|
| 격식 | 신규 고객, 공식 서신 | "귀사와의 협력 가능성에 대해 논의할 수 있어 영광이었습니다." |
| 친근 | 기존 관계, 내부 소통 | "오늘 미팅 감사합니다! 말씀하신 부분 정리해서 보내드립니다." |
| 간결 | 빠른 확인, 짧은 메모 | "미팅 내용 정리입니다. 확인 부탁드립니다." |

**미팅 노트 기반**: 미팅 노트에 기록된 합의사항, 액션 아이템을 기반으로 팔로업 메시지를 자동 구성한다.

### 8.6 Reno AI — 딜 헬스 분석기

각 고객/거래의 **건강도를 5가지 지표로 점수화**하여, 위험 신호를 조기에 감지한다.

**5가지 건강도 지표**:

| 지표 | 측정 방법 | 가중치 |
|------|----------|--------|
| **Engagement** | 최근 30일 상호작용 빈도 | 25% |
| **Timeline** | 거래 진행 속도 vs 예상 기간 | 20% |
| **Stage** | 현재 거래 단계의 정상 여부 | 20% |
| **Budget** | 예산 규모 및 확정 여부 | 15% |
| **Response Rate** | 고객 응답 속도 및 빈도 | 20% |

**등급 체계**:
- **Healthy** (70점 이상): 정상 진행
- **Warning** (40~69점): 주의 필요 — 담당자에게 알림
- **Critical** (40점 미만): 긴급 — Slack DM으로 즉시 알림

**자동 알림**: 매일 오전 9시 크론이 전체 고객 건강도를 점검하고, Critical 등급 고객의 담당자에게 Slack DM을 발송한다.

**대시보드 위젯**: 메인 대시보드에 "위험 거래(Deals at Risk)" 위젯이 표시되어, 한눈에 주의가 필요한 거래를 파악할 수 있다.

### 8.7 주간 리포트 자동 생성

경영진을 위한 **주간 리포트를 AI가 자동 생성**하고, WYSIWYG 편집기에서 수정한 뒤 Notion으로 내보내는 워크플로우이다.

**4섹션 구조**:

| 섹션 | 내용 | 데이터 소스 |
|------|------|-----------|
| **요약** | 금주 주요 성과 및 이슈 요약 | 전체 허브 |
| **세일즈** | 신규 고객, 거래 진행 현황, 건강도 변화 | SalesHub |
| **BD** | 파트너십 진행, 주요 미팅, 합의 사항 | SalesHub |
| **대관** | 규제 동향, 대관 활동, 정부 접촉 | SalesHub, StrategyHub |

각 섹션은 **전주/금주 2컬럼**으로 비교하여 변화를 직관적으로 파악한다.

**워크플로우**:
```
크론 (매주 금요일 15시) ──→ AI 초안 생성 (4섹션 병렬, 15-30초)
                                    │
                                    ▼
                            WYSIWYG 편집기 (TipTap)
                            담당자가 수정·보완
                                    │
                                    ▼
                            Notion 자동 내보내기
                            + 이메일 배포 (계획)
```

**3개월 누적 추이**: 주간 리포트에 3개월간의 주요 지표 추이를 포함하여 장기 트렌드를 파악한다.

### 8.8 Slack 봇 연동

Reno AI는 Slack 앱으로도 동작하여, 영업팀이 Slack 워크스페이스를 떠나지 않고도 AI 기능을 활용할 수 있다.

**@Reno 멘션 응답**: Slack 채널에서 `@Reno [질문]`으로 고객 정보, 미팅 일정, 거래 현황 등을 즉시 질의.

**채널 모니터링**:
- **정형 채널**: `[고객명: XXX]` 패턴의 채널에서 고객명 자동 추출
- **비정형 채널**: AI가 대화 내용을 분석하여 관련 고객/회사명 자동 분류

**슬래시 명령어**:
| 명령어 | 기능 |
|--------|------|
| `/reno memo [내용]` | 고객 메모 빠른 추가 |
| `/reno customer [고객명]` | 고객 컨텍스트 요약 조회 |
| `/reno search [키워드]` | 전체 고객/거래 검색 |

**선제적 알림**: 미팅 리마인더, 위험 고객 경고, 주간 리포트 발행 알림을 Slack DM으로 전달.

### 8.9 음성 녹취 및 미팅 노트

**Fireflies 음성 녹취 연동**: 미팅 녹취가 자동으로 텍스트로 전사되고, AI가 핵심 내용을 요약한다.

**파이프라인**:
```

```

**미팅 노트 기능**:

- 팔로업 이메일 생성 버튼 연동 (Reno AI)

## 9. FinHub — 재무/거래 관리

### 9.1 허브 개요 및 포지셔닝

FinHub는 **거래(Deal)의 전체 라이프사이클과 암호자산 거래를 관리**하는 허브이다. 엑셀 기반의 거래 관리에서 벗어나, 체계적인 워크플로우와 Fireblocks 연동을 통해 재무/컴플라이언스 업무의 정확성과 효율을 높인다.

**재무/컴플라이언스 담당자의 업무 흐름**:
```
딜 생성 ──→ 조건 협의 ──→ 내부 승인 ──→ Fireblocks 거래 실행
   │              │              │              │
   ▼              ▼              ▼              ▼
FinHub에서    FinHub에서    승인 워크플로우   트랜잭션 모니터링
딜 등록      조건 기록      자동 실행        및 정산 확인
```

### 9.2 딜(Deal) 라이프사이클 관리

**딜 코드 체계**

각 거래는 고유한 코드로 식별된다:
```
LCH_2025E01A_USDT_1
 │    │     │    │
 │    │     │    └── 순번
 │    │     └─────── 거래 자산
 │    └───────────── 거래 식별자
 └────────────────── 고객/상대방 코드
```

**딜 상태 워크플로우**:
```
Draft ──→ In Progress ──→ Completed ──→ Settled
  │            │              │
  └── 취소 ────└── 보류 ──────└── 분쟁 처리
```

**딜 유형별 관리**:
| 유형 | 설명 | 특성 |
|------|------|------|
| **Earn** | 이자 수익 상품 | 기간 고정, 이자율 명시 |
| **Booster Range** | 범위 기반 수익 상품 | 상한/하한 가격 설정 |
| **Riskless BTC** | 무위험 BTC 상품 | 원금 보장 구조 |

**딜 상세 화면**: 딜 코드, 상태, 유형, 관련 자산, 금액, 기간, 상대방 정보, 승인 이력, 관련 트랜잭션을 한 화면에서 확인한다.

### 9.3 암호자산 거래 — Fireblocks 연동

Fireblocks는 기관급 디지털자산 관리 플랫폼으로, FinHub와 연동하여 안전한 암호자산 거래를 지원한다.

**연동 구조**:
```
FinHub (딜 관리) ──→ Fireblocks API ──→ 블록체인
       │                    │
       │              ┌─────┴─────┐
       │              │  Vault    │
       │              │  (금고)   │
       │              │           │
       │              │  Wallet A │
       │              │  Wallet B │
       │              └───────────┘
       │
       └── 트랜잭션 상태 모니터링
```

**지갑(Wallet) 관리**: 자산별 지갑 생성/조회, 잔고 확인, 입출금 이력

**트랜잭션 흐름**: 생성 → 내부 승인 → Fireblocks 서명 → 블록체인 전파 → 확인

**자산 유형별 관리**: USDT, USDC, BTC, ETH 등 주요 암호자산 지원

### 9.4 CSV 대량 임포트

기존 엑셀/CSV로 관리하던 거래 데이터를 FinHub으로 대량 이관하는 기능이다.

**워크플로우**:
```
CSV 업로드 ──→ 미리보기 ──→ 필드 매핑 ──→ 검증 ──→ 확정 임포트
                  │              │            │
                  ▼              ▼            ▼
             데이터 미리보기   컬럼 매칭     오류 표시
             샘플 5행 표시    자동 추천     행별 오류 이유
```

**지원 데이터**: 고객 정보, 거래 내역, 자산 정보

**오류 처리**: 행별 오류를 표시하며, 전체 롤백 또는 오류 행만 제외하고 임포트하는 옵션을 제공한다.

### 9.5 거래 승인 워크플로우

거래의 내부 승인을 체계적으로 관리하는 워크플로우이다.

**승인 단계**:
```
담당자 요청 ──→ 팀장 검토 ──→ 본부장 승인 ──→ 실행
                   │              │
                   └── 반려 ──────└── 반려 (사유 기록)
```

**감사 로그**: 모든 승인/반려 이력이 자동 기록되며, 언제든 감사 추적이 가능하다.

### 9.6 대시보드 및 리포팅

**거래 현황 대시보드**:
- 상태별 (Draft/In Progress/Completed/Settled) 건수 및 금액
- 유형별 (Earn/Booster Range/Riskless BTC) 분포
- 자산별 (USDT/BTC/ETH) 포지션

**엔티티(Entity) 관리**: 거래 상대방의 법인 정보, 연락처, 거래 이력을 관리한다.

**재무 리포트**: 기간별 거래 요약, 자산 포지션 변화, 수익률 분석을 자동 생성한다.

### 9.7 AI 기반 거래 분석

AI가 거래 패턴을 분석하여 이상 징후를 감지하고 위험을 평가한다.

**이상 거래 패턴 감지**:
- 평소와 다른 거래 규모
- 비정상적인 거래 빈도 변화
- 새로운 상대방과의 대규모 거래

**위험도 자동 평가**: 거래 특성에 따라 Low/Medium/High 위험 등급을 자동 부여한다.

**컴플라이언스 자동 점검**: AML 규정에 따른 자동 체크리스트 검증을 수행한다.

## 10. OnboardingHub — 고객 온보딩

### 10.1 허브 개요 및 포지셔닝

OnboardingHub는 **신규 고객 온보딩의 전 과정을 디지털화**한 허브이다. 종이 서류 기반의 KYC/AML 프로세스를 OCR 자동 인식과 듀얼 승인 워크플로우로 전환하여, 정확성을 높이고 처리 시간을 단축한다.

**역할 분담**:
| 역할 | 담당 업무 |
|------|----------|
| **운영팀** | 서류 수집, 초기 검토, 고객 소통 |
| **AML팀** | 자금세탁 위험 평가, AML 심사 |
| **준법감시인** | 최종 듀얼 승인 (승인자 1) |
| **비즈니스본부장** | 최종 듀얼 승인 (승인자 2) |

### 10.2 온보딩 프로세스 전체 흐름

**고객 유형별 온보딩 경로**:
| 유형 | 필요 서류 | 예상 소요 |
|------|----------|----------|
| **개인** | 신분증, 주소 증명 | 2-3일 |
| **법인** | 사업자등록증, 법인등기부, 대표 신분증, 주주명부 | 5-7일 |
| **기관** | 법인 서류 + 투자 정책서, 이사회 결의서 | 7-14일 |

**전체 프로세스 다이어그램**:
```
고객 ──→ 업로드 링크 ──→ 서류 제출 ──→ OCR 자동 인식
                                            │
                                            ▼
                                   운영팀 초기 검토
                                            │
                                            ▼
                                   AML팀 위험 평가
                                            │
                                            ▼
                                   듀얼 승인
                                   (준법감시인 + 본부장)
                                            │
                                            ▼
                                   온보딩 완료
                                   고객 활성화
```

### 10.3 6단계 서류 검토 워크플로우

OnboardingHub의 핵심은 서류 검토를 **6단계로 체계화**한 워크플로우이다.

```
Draft ──→ Ops Confirmed ──→ AML Reviewing ──→ AML Completed
  (1)         (2)               (3)               (4)
                                                    │
                                                    ▼
                              Approved ←── Final Confirmed
                                (6)            (5)
```

| 단계 | 명칭 | 담당자 | 행위 |
|------|------|--------|------|
| 1 | **Draft** | 시스템 | 서류 제출 시 자동 생성 |
| 2 | **Ops Confirmed** | 운영팀 | 서류 완전성 확인, OCR 결과 검증 |
| 3 | **AML Reviewing** | AML팀 | 자금세탁 위험 평가 시작 |
| 4 | **AML Completed** | AML팀 | AML 심사 완료, 위험 등급 부여 |
| 5 | **Final Confirmed** | 운영팀/AML팀 | 최종 확인, 듀얼 승인 요청 생성 |
| 6 | **Approved** | 준법감시인+본부장 | 듀얼 승인 완료, 온보딩 확정 |

**반려 처리**: 각 단계에서 반려(Rejection)할 수 있으며, 반려 사유가 기록된다. 고객에게 재제출 요청이 전달되고, 재제출 시 해당 단계부터 재시작한다.

### 10.4 GCP Vision OCR 자동 인식

Google Cloud Vision API를 활용하여 한국어 서류를 자동으로 인식하고 핵심 필드를 추출한다.

**지원 서류 유형**:
- 신분증 (주민등록증, 운전면허증, 여권)
- 사업자등록증
- 법인등기부등본
- 주주명부
- 재무제표

**자동 인식 필드**:
| 서류 | 추출 필드 |
|------|----------|
| 신분증 | 성명, 생년월일, 주소 |
| 사업자등록증 | 법인명, 사업자등록번호, 대표자명, 주소, 업종 |
| 법인등기부 | 법인명, 등기번호, 설립일, 대표이사, 본점 소재지 |

**신뢰도 스코어**: 각 추출 필드에 신뢰도 스코어를 부여하며, 기준 미달(예: 70% 미만) 시 수동 검증 트리거가 활성화된다.

**한국어 특화**: 한국어 서류의 고유한 레이아웃과 표현을 학습한 패턴 인식 로직이 적용되어 있다.

### 10.5 듀얼 승인 프로세스

금융 규제 요건을 충족하기 위해 **두 명의 승인자가 모두 승인해야** 온보딩이 완료되는 구조이다.

**승인자**:
| 승인자 | 역할 | 검토 관점 |
|--------|------|----------|
| **준법감시인** (Compliance Officer) | 규제 적합성 확인 | KYC/AML 요건 충족 여부 |
| **비즈니스본부장** (Business Head) | 비즈니스 적합성 확인 | 고객 적합성, 리스크 수용 여부 |

**흐름**:
```
최종 확인 (5단계) ──→ 듀얼 승인 요청 자동 생성
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
             준법감시인 승인      비즈니스본부장 승인
                    │                   │
                    └─────────┬─────────┘
                              │
                              ▼
                      양측 모두 승인 시
                      온보딩 완료 (6단계)
```

**승인 기한**: 승인 요청 후 3영업일 이내 미처리 시 에스컬레이션 알림이 발송된다.

### 10.6 KYC/AML 컴플라이언스

**KYC 체크리스트**:
- [ ] 고객확인(CDD): 신원 확인, 실소유자 확인
- [ ] 강화 고객확인(EDD): 고위험 고객 대상 추가 조사
- [ ] PEP 검사: 정치적 주요인물 해당 여부
- [ ] 제재 리스트 대조: 국내외 제재 대상 여부

**AML 위험 등급**:
| 등급 | 기준 | 조치 |
|------|------|------|
| **Low** | 일반 개인, 소액 거래 | 기본 CDD |
| **Medium** | 법인, 중규모 거래 | 강화 CDD |
| **High** | 고위험 국적, 대규모 거래, PEP | EDD + 지속 모니터링 |

**정기 재검토(Re-KYC)**: 위험 등급에 따라 1년(High) / 2년(Medium) / 3년(Low) 주기로 재검토를 실시한다.

### 10.7 고객 포털

고객이 **로그인 없이 서류를 제출**할 수 있는 토큰 기반 업로드 시스템이다.

**워크플로우**:
```
운영팀이 업로드 링크 생성 ──→ 고객에게 링크 전달 (이메일/메신저)
                                      │
                                      ▼
                              고객이 링크 접속
                              (로그인 불필요)
                                      │
                                      ▼
                              서류 드래그&드롭 업로드
                                      │
                                      ▼
                              운영팀에 알림 → 검토 시작
```

**보안**: 각 업로드 링크는 고유 토큰으로 보호되며, 유효기간(기본 7일)이 지나면 자동 만료된다.

**진행 상태 조회**: 고객은 동일 링크에서 자신의 온보딩 진행 상태를 확인할 수 있다.

### 10.8 감사 로그 및 보고

**감사 추적(Audit Trail)**: 온보딩 프로세스의 모든 작업 — 서류 업로드, 상태 변경, 승인/반려, 코멘트 — 이 `ReviewAuditLog`에 자동 기록된다. 누가, 언제, 무엇을 했는지 완전한 이력을 보존한다.

**규제 보고용 데이터 추출**: 감독기관 요청 시 특정 고객의 온보딩 전체 이력을 즉시 추출하여 제공할 수 있다.

**온보딩 통계 대시보드**:
- 진행 중 / 완료 / 반려 건수
- 평균 처리 시간 (단계별)
- 병목 단계 분석

## 11. StrategyHub — 전략 문서 + Context Pool

### 11.1 허브 개요 및 포지셔닝

StrategyHub는 **전략 문서 생성·협업 리뷰·산업/규제 정보 수집**을 담당하는 허브이다. Collector 에이전트가 외부 정보를 자동 수집하고, AI 기반 문서 편집 환경에서 전략 문서를 생성·리뷰한다.

**핵심 가치: "흩어진 정보를 조직의 지식으로 전환"**

```
                    ┌─────────────────────────┐
                    │      StrategyHub        │
                    │                         │
                    │  ┌─────────┐ ┌─────────┐ │
                    │  │Collector│ │ 문서생성 │ │
                    │  │정보수집 │ │ AI 협업  │ │
                    │  └────┬────┘ └────┬────┘ │
                    │       └─────┬─────┘      │
                    │             ▼             │
                    │      Context Pool         │
                    │    (전사 지식 저수지)       │
                    └──────┬──────┬─────────────┘
                           │      │
                    ┌──────┘      └──────┐
                    ▼                    ▼
              각 허브로 전달          경영진 리뷰
              (산업 동향, 규제)      (전략 문서)
```

**다른 허브와의 관계**:
- **SalesHub → StrategyHub**: 고객 동향, 영업 인사이트가 전략 분석의 원재료
- **FinHub → StrategyHub**: 거래 패턴, 시장 데이터가 재무 분석의 기반
- **OnboardingHub → StrategyHub**: 고객 유형별 온보딩 트렌드가 사업 전략 수립에 활용
- **StrategyHub → 각 허브**: 산업 동향, 규제 변화, 전략 문서가 현업 의사결정을 지원

### 11.2 Context Pool로서의 역할

각 허브가 업무 도메인별 데이터를 다루는 것과 마찬가지로, StrategyHub는 **산업 동향·규제 정보·전략 문서** 도메인을 담당한다. 동시에 허브간 공유가 필요한 전사적 지식을 Context Pool에 축적하여 다른 허브에서도 활용할 수 있게 한다.

**정보의 흐름**:
```
[ 외부 정보 ]                    [ 내부 정보 ]

규제 기관 발표 ──┐               ┌── SalesHub (고객 동향)
산업 뉴스 ───────┤               ├── FinHub (거래 패턴)
경쟁사 동향 ─────┤    Context    ├── OnboardingHub (온보딩 트렌드)
시장 리포트 ─────┼──→  Pool  ←──┤
학술 논문 ───────┤               ├── 미팅 녹취 요약
파트너사 소식 ───┘               └── 내부 논의 기록
                       │
                       ▼
              [ 전략적 산출물 ]
              · 시장 분석 보고서
              · 전략 제안서
              · 규제 대응 문서
              · 경영진 브리핑
```

**선순환 구조**: Context Pool에 축적된 지식이 풍부할수록 AI 에이전트의 문서 생성 품질이 높아지고, 높은 품질의 문서는 더 많은 리뷰와 피드백을 유발하며, 이 피드백이 다시 Context Pool을 풍부하게 한다.

### 11.3 자동 정보 수집 에이전트 (Collector)

Collector는 외부 정보를 **자동으로 수집·분류·저장**하는 백그라운드 에이전트이다.

**3가지 수집 플러그인**:

| 플러그인 | 소스 유형 | 수집 방법 |
|---------|----------|----------|
| **RSS** | 뉴스, 블로그 | RSS 피드 파싱 |
| **Web Scrape** | 정부 사이트, 업계 포털 | HTML 크롤링 |
| **PDF Report** | 정책 문서, 리서치 리포트 | PDF 다운로드 + 텍스트 추출 |

**수집 카테고리**:
- **Regulatory** (규제): 금융위원회, 금감원, 국제 규제 기관 발표
- **Industry** (산업): 디지털자산 시장 동향, 경쟁사 소식, 파트너 동향

**자동 스케줄링**: 매시간 자동 실행. 중복 제거 로직으로 동일 기사의 재수집을 방지하며, 수집 실패 시 3회 재시도(5초, 10초 백오프).

**수집 관리 UI**: 소스 등록/수정/비활성화, 수집 현황 대시보드, 실행 로그 조회.

**향후 확장 계획**:
- Notion 워크스페이스 데이터 수집
- Slack 채널 아카이브 연동
- 이메일 수신함 자동 수집

### 11.4 AI 기반 문서 생성 워크플로우

StrategyHub에서 생성하는 문서는 **6가지 유형**으로 체계화되어 있다.

| 코드 | 유형 | 설명 | 예시 |
|------|------|------|------|
| **RPT** | 보고서 | 시장 분석, 데이터 보고 | "2026 디지털자산 수탁시장 동향" |
| **PRP** | 제안서 | 전략, 파일럿, 협의 건의 | "코빗-웨이브릿지 LP 파일럿 테스트 승인 요청" |
| **ANL** | 분석 | 깊이 있는 주제 분석 | "전사 AWS 인프라 비용 분석" |
| **MTG** | 회의록 | 미팅 내용 정리 | "이사회 회의록" |
| **REG** | 규제 문서 | 규제 대응 자료 | "디지털자산기본법 대응 방안" |
| **DSH** | 대시보드 | 시각화/대시보드 | "월간 KPI 대시보드" |

**프로젝트 코드 체계**: `{유형}-{YYYYMMDD}-{키워드}`
- 예: `RPT-20260227-da-custody-market`
- 예: `PRP-20260304-lp-pilot-test`

**이해관계자별 톤/스타일 가이드**:
| 대상 | 톤 | 특징 |
|------|-----|------|
| 경영진 (대표, CFO) | 간결, 의사결정 중심 | 핵심 수치와 결론 우선, 배경 최소화 |
| 규제기관 (금융위, 금감원) | 격식, 규제 용어 정확 | 법적 요건 명시, 근거 자료 첨부 |
| 투자자 (VC, PE) | 성장 잠재력 강조 | 시장 기회, 경쟁 우위, 재무 전망 |
| 파트너사 | 상호 이익 강조 | 협력 시너지, 구체적 제안 |

**용어집 기반 일관성**: "디지털자산" vs "가상자산", "수탁" vs "커스터디" 등 혼용되기 쉬운 용어를 통합 용어집으로 관리하여 문서 전체의 일관성을 유지한다.

### 11.5 협업 리뷰 및 AI 자동 반영

StrategyHub의 가장 혁신적인 기능은 **리뷰어의 피드백을 AI가 자동으로 문서에 반영**하여 새 버전을 생성하는 워크플로우이다.

**블록 단위 인라인 코멘트**:

문서를 논리적 블록(단락, 표, 코드 블록 등)으로 나누어, 각 블록에 대해 개별적으로 코멘트를 달 수 있다. "이 부분의 수치를 업데이트해주세요", "톤을 좀 더 격식체로", "출처를 추가해주세요" 등의 구체적 피드백이 가능하다.

**AI 자동 반영 워크플로우**:
```
리뷰어가 블록별 코멘트 작성
         │
         ▼
작성자가 "AI 리뷰 반영" 클릭
         │
         ├── 반영할 코멘트 선택 (기본: 전체)
         ├── 추가 지시사항 입력 (선택)
         │
         ▼
Claude API가 코멘트를 문서에 반영
         │
         ▼
새 버전 자동 생성 (v1.0 → v1.1)
         │
         ├── 반영된 코멘트 자동 "해결" 표시
         ├── AI 반영 요약 기록
         └── Diff 뷰어로 변경사항 확인
```

**버전 관리**:
- Minor 버전 (v1.0 → v1.1): AI 반영 또는 소규모 수정
- Major 버전 (v1.x → v2.0): 구조적 변경, 수동 지정

**리뷰 워크플로우**: Draft → Review → Published
- **Draft**: 작성자만 수정 가능
- **Review**: 리뷰어가 코멘트 작성, AI 반영 반복
- **Published**: Admin 승인 후 최종 공개

### 11.6 문서 뷰어 및 배포

**마크다운 기반 고품질 렌더링**: 테이블, 코드 블록, 이미지, 인용문 등을 깔끔하게 렌더링하며, 자동 목차(TOC) 생성과 섹션 네비게이션을 지원한다.

**Published 문서 열람**: 역할 기반 접근 제어로, 권한에 따라 열람 가능한 문서가 결정된다.

**향후 배포 채널**:
- Notion 자동 내보내기
- PDF 변환 및 다운로드
- 이메일 배포

### 11.7 규제/컴플라이언스 문서 관리

금융업의 핵심 리스크인 **규제 변화에 체계적으로 대응**하기 위한 전용 기능이다.

**규제 정보 중앙화**: 디지털자산기본법, 특금법, 각종 금융위/금감원 가이드라인을 StrategyHub에서 중앙 관리한다.

**컴플라이언스 체크리스트**: 문서 작성 시 자동으로 관련 규제 체크리스트를 검증하여, 규제 리스크를 사전에 방지한다.

**규제 변화 모니터링**: Collector가 규제 기관 RSS/웹사이트를 매시간 모니터링하여 새로운 규제 발표를 자동 수집한다.

**규제기관 대응 문서 템플릿**: 금융위원회, 금감원 등에 제출하는 문서의 표준 템플릿을 제공하여 대응 속도를 높인다.

## 15. AI 에이전트 체계

### 허브별 전문 에이전트

| 에이전트 | 소속 | 주요 기능 | 사용 LLM |
|---------|------|----------|---------|

| **문서 편집 AI** | StrategyHub | 리뷰 반영, 톤 조정, 품질 검증, 문서 초안 생성 | Claude |
| **위험평가 AI** | HubManager | 가상자산 위험 설명서 자동 생성 | Claude |
| **OCR AI** | OnboardingHub | 서류 자동 인식, 필드 추출, 신뢰도 평가 | GCP Vision |
| **거래 분석 AI** | FinHub | 이상 거래 감지, 위험도 평가 | Claude |

### 내부용 vs 외부용 페르소나 전략

동일한 에이전트도 사용 맥락에 따라 **다른 페르소나**로 동작한다:

| 구분 | 내부용 | 외부용 |
|------|--------|--------|
| **톤** | 친근, 반말 허용 | 격식, 경어체 |
| **이모지** | 허용 | 금지 |
| **정보 범위** | 내부 데이터 전체 접근 | 공개 가능 정보만 |
| **응답 스타일** | 간결, 직설적 | 정중, 설명적 |

### 대화 컨텍스트 관리 및 기억 구조

AI 에이전트는 대화의 맥락을 유지하기 위해 **세션 기반 대화 관리**를 사용한다.

```
세션 시작 ──→ 사용자 질의 ──→ Context Pool에서 관련 정보 조회
                                        │
                                        ▼
                               AI 응답 생성 (컨텍스트 반영)
                                        │
                                        ▼
                               대화 로그 저장 (1년 보존)
```

### 에이전트 성능 평가 및 개선 루프

1. **사용량 모니터링**: 에이전트별 호출 횟수, 토큰 사용량, 응답 시간
2. **품질 검토**: 어드민이 대화 로그를 샘플링하여 품질 점검
3. **피드백 반영**: 사용자 피드백을 페르소나 정의에 반영
4. **A/B 테스트**: 프롬프트 변경 시 이전 버전과 품질 비교

## 16. Context Pool 운영

### 8가지 입력 파이프라인 상세

| # | 파이프라인 | 수집 주기 | 처리 방식 | Context Pool 반영 |
|---|----------|----------|----------|-----------------|
| 1 | **Slack 메시지** | 실시간 | 채널 모니터링 → AI 분류 → 고객명 추출 | 고객 컨텍스트 |
| 2 | **음성 녹취** | 미팅 직후 | Fireflies 전사 → AI 요약 | 미팅 컨텍스트 |
| 3 | **문서 OCR** | 업로드 즉시 | GCP Vision → 필드 추출 | 고객 온보딩 컨텍스트 |
| 4 | **수동 입력** | 즉시 | 사용자 직접 입력 → 구조화 | 해당 컨텍스트 |
| 5 | **이메일** (계획) | 수신 시 | 이메일 파싱 → AI 분류 | 커뮤니케이션 컨텍스트 |
| 6 | **외부 API** | 일/주 배치 | API 호출 → 데이터 정규화 | 시장/규제 컨텍스트 |
| 7 | **크론 배치** | 일/주/월 | 자동 집계 → AI 요약 | 통계 컨텍스트 |
| 8 | **Collector** | 매시간 | RSS/웹/PDF → AI 분류 | 산업/규제 컨텍스트 |

### 허브간 Context Pool 연동

```
StrategyHub Collector ──→ 산업/규제 Context Pool ──┐
SalesHub 고객 활동 ─────→ 고객 Context Pool ────────┼──→ 크로스 허브 활용
FinHub 거래 데이터 ─────→ 거래 Context Pool ────────┤
OnboardingHub KYC ──────→ 온보딩 Context Pool ─────┘
```

각 허브의 Context Pool은 다른 허브에서도 참조 가능하다. 예를 들어 SalesHub의 고객 브리핑에 StrategyHub의 산업 동향이 포함되고, FinHub의 거래 분석에 규제 변화가 반영된다.

### 컨텍스트 품질 관리

- **자동 갱신**: 새 정보 유입 시 즉시 반영, 크론으로 일 1회 전체 재요약
- **중복 제거**: 동일 소스의 중복 정보 자동 필터링
- **관련성 감쇠**: 오래된 정보의 가중치 자동 감소

### 개인정보 보호 및 접근 제어

- **역할 기반 접근**: 사용자 역할에 따라 접근 가능한 컨텍스트 범위 제한
- **데이터 마스킹**: 민감 정보(주민번호, 계좌번호 등)는 자동 마스킹
- **보존 정책**: 대화 로그 1년 보존 후 자동 삭제, 감사 로그는 법적 요건에 따라 장기 보존

## 20. 2027 이후 비전

### AI 자율 에이전트

현재의 AI 에이전트는 사용자의 요청에 **반응(Reactive)**하는 수준이다. 2027년에는 에이전트가 **능동적(Proactive)**으로 행동하는 단계를 목표로 한다.

- 사람의 개입 없이 정기 분석 실행 및 리포트 배포
- 이상 징후 감지 시 자동으로 관련 담당자에게 브리핑 + 대응 제안
- 크로스 허브 데이터를 종합한 전략적 인사이트 자동 도출

### 크로스 허브 인사이트 엔진

각 허브의 Context Pool을 기반으로, **허브를 넘나드는 통합 분석**이 가능해진다.

```
SalesHub 데이터 ────┐
FinHub 데이터 ──────┼──→ 크로스 허브 인사이트 엔진 ──→ 경영진 대시보드
OnboardingHub 데이터 ┤                                      │
StrategyHub 동향 ───┘                                      ▼
                                                   "3분기 기관 고객 온보딩 증가 →
                                                    Earn 상품 수요 40% 증가 예상 →
                                                    유동성 확보 필요"
```

### 글로벌 확장

- 다국어 지원 (영어 우선)
- 해외 규제 프레임워크 적용 (MiCA, MAS 등)
- 글로벌 파트너사 허브 접근 지원
