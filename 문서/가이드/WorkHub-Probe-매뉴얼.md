# WorkHub Probe 매뉴얼

> **문서 버전**: v2.0 | **최종 업데이트**: 2026. 03. 16 | **대상 독자**: 전 직원

---

## 1장. WorkHub Probe란?

### 한 줄 정의

**WorkHub의 모든 서비스가 정상 동작하는지 24시간 자동으로 감시하는 품질 관리 시스템**입니다.

### 쉽게 이해하기

WorkHub Probe는 건물의 **CCTV + 화재경보기**와 같습니다.

- **CCTV**처럼, 우리 서비스의 모든 주요 기능을 정기적으로 촬영(테스트)합니다.
- **화재경보기**처럼, 문제가 감지되면 즉시 Slack으로 알려줍니다.
- **관제실 모니터**처럼, 대시보드에서 전체 현황을 한눈에 볼 수 있습니다.

사람이 직접 매번 로그인하고, 페이지를 열어보고, 버튼을 눌러보는 대신, Probe가 가상 브라우저를 열어 실제 사용자와 동일한 동작을 자동으로 반복 수행합니다.

### 기존 상황과 문제점

| 항목 | 기존 (Before) | 문제점 |
|------|--------------|--------|
| 테스트 방식 | 개발자가 수동으로 확인 | 사람에 의존, 누락 빈번 |
| 테스트 범위 | 각 허브가 독립적으로 일부만 테스트 | 허브 간 연동(SSO 등) 미검증 |
| 장애 감지 | 사용자 신고 후 인지 | 대응이 늦어 피해 확대 |
| 테스트 도구 | 5개 리포에 각각 다른 방식 | 중복 코드, 비일관적 품질 |
| 결과 관리 | 기록 없음 | 추적 불가, 동일 에러 반복 |

### Probe 도입 후 변화

| 항목 | 도입 후 (After) |
|------|----------------|
| 테스트 방식 | 매일 2회 자동 실행 (오전 6시, 오후 6시) |
| 테스트 범위 | 4개 허브 통합 + 허브 간 SSO 플로우 검증 |
| 장애 감지 | 문제 발생 즉시 Slack 알림 (해결 방법 포함) |
| 테스트 도구 | 단일 공유 패키지(`@workhub/probe`)로 통합 |
| 결과 관리 | 대시보드에서 전 이력 조회 + 에러 패턴 DB 축적 |

## 2장. 왜 필요한가?

### 서비스 안정성 확보

고객이 "로그인이 안 됩니다"라고 연락하기 **전에** 우리가 먼저 문제를 발견합니다. Probe는 실제 사용자의 동선을 그대로 따라하기 때문에, 사용자가 겪을 수 있는 문제를 미리 발견할 수 있습니다.

### 비용 절감

수동 QA에 투입되던 시간을 대폭 줄입니다. 개발자가 매번 "로그인 되나?", "페이지 열리나?", "API 응답 오나?"를 직접 확인하지 않아도 됩니다.

| 작업 | 수동 소요 시간 | Probe 소요 시간 |
|------|--------------|----------------|
| 4개 허브 로그인 확인 | ~20분 | 2분 (자동) |
| SSO 플로우 검증 | ~30분 | 3분 (자동) |
| 주요 페이지 로딩 확인 | ~40분 | 5분 (자동) |
| **일일 합계** | **~90분** | **~10분 (무인)** |

### 배포 품질 보장

새 기능을 배포하기 전, Probe를 실행하면 기존 기능이 깨지지 않았는지 자동으로 확인할 수 있습니다. "배포했더니 다른 기능이 안 된다"는 상황을 예방합니다.

### 팀 간 투명성

대시보드를 통해 개발팀뿐 아니라 기획팀, 경영진도 서비스 품질 현황을 실시간으로 확인할 수 있습니다.

## 3장. 무엇을 감시하는가?

### 감시 대상 서비스

| 허브 | 역할 | 감시 항목 |
|------|------|----------|
| **HubManager** | 중앙 관리 (SSO 인증, 허브 관리) | 로그인, 어드민 페이지, 사용자 관리 |
| **SalesHub** | CRM, Reno AI 챗봇 | 고객 목록, 메모, AI 응답 |
| **FinHub** | 딜 관리, CSV 업로드 | 딜 목록, 데이터 import |
| **OnboardingHub** | 고객 온보딩 | 온보딩 플로우, 문서 업로드 |

### 감시 항목 상세

#### SSO 인증 플로우 (가장 중요)

WorkHub의 핵심인 **통합 로그인(SSO)** 을 검증합니다. 한 곳에서 로그인하면 모든 허브에 접근할 수 있어야 하고, 로그아웃하면 모든 곳에서 동시에 로그아웃되어야 합니다.

```
[검증 흐름]

① HubManager 로그인 → 인증 확인 ✓
② SalesHub 이동 → 추가 로그인 없이 접근 가능 ✓
③ FinHub 이동 → 추가 로그인 없이 접근 가능 ✓
④ 로그아웃 → 전체 허브에서 세션 종료 ✓
⑤ 각 허브 메인 페이지 정상 로딩 ✓
```

#### 주요 페이지 로딩

각 허브의 핵심 페이지가 에러 없이 정상적으로 표시되는지 확인합니다.

#### API 응답 검증

서버가 요청에 올바르게 응답하는지 확인합니다. (예: 사용자 정보 조회, 고객 목록 호출 등)

#### 에러 패턴 수집

테스트 중 발견된 에러를 자동으로 분류하여 데이터베이스에 축적합니다.

| 에러 분류 | 의미 | 예시 |
|----------|------|------|
| TIMEOUT | 응답 시간 초과 | 페이지가 30초 넘게 로딩 |
| AUTH | 인증 오류 | 로그인했는데 접근 거부 |
| NOT_FOUND | 페이지 없음 | 존재하지 않는 URL 접근 |
| SERVER_ERROR | 서버 내부 오류 | 500 에러 발생 |
| SELECTOR | 화면 요소 없음 | 버튼이나 입력칸이 사라짐 |

## 4장. 어떻게 동작하는가?

### 전체 동작 흐름

```
┌─────────────────────────────────────────────────────────────┐
│                    WorkHub Probe 동작 흐름                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ① 스케줄러                  ② 가상 브라우저                  │
│  ┌──────────┐               ┌──────────────┐               │
│  │ 매일     │──── 시작 ───→│ Chrome 자동   │               │
│  │ 6AM/6PM  │               │ 로그인, 클릭  │               │
│  └──────────┘               │ 페이지 이동   │               │
│                             └──────┬───────┘               │
│                                    │                        │
│                            결과 수집 │                        │
│                                    ▼                        │
│  ④ Slack 알림               ③ 결과 저장                      │
│  ┌──────────┐               ┌──────────────┐               │
│  │ 실패 시   │◀── 즉시 ────│ 대시보드 DB   │               │
│  │ 팀 알림   │               │ 에러 패턴 DB  │               │
│  │ +해결책   │               └──────────────┘               │
│  └──────────┘                      │                        │
│                                    ▼                        │
│                             ⑤ 대시보드                       │
│                             ┌──────────────┐               │
│                             │ 웹에서 확인   │               │
│                             │ 성공률, 추세  │               │
│                             └──────────────┘               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 단계별 설명

**① 스케줄러가 테스트를 시작합니다**

매일 오전 6시와 오후 6시에 자동으로 테스트가 시작됩니다. 수동으로 원하는 시점에 실행할 수도 있습니다.

**② 가상 브라우저가 서비스를 이용합니다**

실제 Chrome 브라우저를 열고, 사람이 하는 것처럼 로그인하고, 페이지를 이동하고, 버튼을 클릭합니다. 화면이 제대로 뜨는지, 에러가 나지 않는지 자동으로 판단합니다.

**③ 결과가 데이터베이스에 저장됩니다**

각 테스트의 성공/실패, 소요 시간, 에러 내용이 모두 기록됩니다. 같은 에러가 반복되면 "에러 패턴"으로 자동 분류되어 추적됩니다.

**④ 실패 시 Slack으로 즉시 알림이 갑니다**

테스트가 실패하면 담당 채널에 즉시 알림이 전송됩니다. 단순한 "실패" 알림이 아니라, 에러 패턴 DB에서 **알려진 해결 방법**까지 함께 제안합니다.

Slack 알림 예시:

```
❌ WBHubManager - Cross-Hub SSO

Status: FAILED
Success Rate: 60.0%
Duration: 45.2s
Steps: 3/5 passed

Failed Steps:
❌ SSO-03: FinHub 인증 확인
  Error: 401 Unauthorized
  💡 쿠키 도메인 설정 확인 (성공률 85%)
  💡 Nginx proxy_pass 헤더 확인 (성공률 70%)
```

**⑤ 대시보드에서 전체 현황을 확인합니다**

웹 브라우저에서 대시보드에 접속하면 전체 허브의 테스트 상태를 한눈에 볼 수 있습니다.

## 5장. 대시보드 사용법

### 접속 방법

| 환경 | URL |
|------|-----|
| 로컬 | http://localhost:3080 |
| 프로덕션 | http://workhub.biz/probe |

### 화면 구성

대시보드는 6개의 주요 화면으로 구성되어 있습니다.

#### 메인 대시보드 (`/`)

서비스 전체의 건강 상태를 한눈에 보여줍니다.

| 영역 | 표시 내용 |
|------|----------|
| 테스트 성공률 | 최근 테스트의 전체 성공 비율 (%) |
| 총 에러 패턴 | 발견된 에러 유형의 수와 해결된 수 |
| 최근 테스트 실행 | 최근 실행된 테스트 목록 (성공/실패 표시) |
| 주요 에러 패턴 | 가장 자주 발생하는 에러 Top 5 |

#### Cross-Hub 개요 (`/cross-hub`)

4개 허브의 상태를 카드 형태로 한눈에 보여줍니다.

- **초록 카드**: 최근 테스트 성공
- **빨간 카드**: 최근 테스트 실패
- **회색 카드**: 테스트 기록 없음

각 카드에는 마지막 테스트 시간, 성공/실패 스텝 수, 30일 통계가 표시됩니다.

#### 에러 패턴 (`/error-patterns`)

반복적으로 발생하는 에러를 추적합니다.

- 에러 유형별 필터링 (TIMEOUT, AUTH, SERVER_ERROR 등)
- 허브별 필터링
- 각 에러에 대한 **알려진 해결 방법** 확인 가능
- 에러 발생 빈도와 최근 발생 시각 표시

#### 테스트 결과 (`/test-results`)

모든 테스트 실행 이력을 시간순으로 조회합니다.

#### 체크리스트 (`/debugging-checklists`)

에러 유형별 디버깅 체크리스트를 제공합니다. (SSO, 데이터베이스, Nginx 등)

#### 템플릿 (`/templates`)

테스트 스크립트 작성 시 활용할 수 있는 템플릿 목록입니다.

## 6장. 도입 효과

### 정량적 효과

| 지표 | 도입 전 | 도입 후 | 개선율 |
|------|--------|--------|--------|
| API 테스트 커버리지 | 7% (394개 중 28개) | 목표 80%+ | +73%p |
| 페이지 테스트 커버리지 | 28% (68개 중 19개) | 목표 60%+ | +32%p |
| 허브 간 SSO 테스트 | 0건 | 5건 (자동 실행) | 신규 |
| 수동 QA 소요 시간 | 일 90분 | 일 0분 (자동) | -100% |
| 테스트 파일 수 (활성) | 47개 (파편화) | 통합 패키지 기반 | 구조화 |
| 에러 패턴 추적 | 없음 | 자동 수집 + 해결책 DB | 신규 |

### 정성적 효과

**장애 사전 감지**: 사용자가 문제를 경험하기 전에 팀이 먼저 인지합니다. 새벽에 발생한 장애도 오전 6시 테스트에서 자동으로 발견됩니다.

**에러 해결 시간 단축**: 동일한 에러가 다시 발생했을 때, 과거에 어떻게 해결했는지 DB에서 바로 확인할 수 있습니다. "이 에러 전에 어떻게 고쳤더라?"를 더 이상 기억에 의존하지 않습니다.

**팀 간 품질 가시성**: 기획자, PM, 경영진도 대시보드에서 각 허브의 품질 상태를 실시간으로 확인할 수 있습니다. "그 기능 잘 돌아가요?"라는 질문에 데이터로 답할 수 있습니다.

**배포 자신감 향상**: 새 기능을 배포하기 전에 Probe를 실행하면, 기존 기능이 정상인지 자동으로 확인됩니다. 배포 후 "다른 기능이 깨졌다"는 상황을 예방합니다.

## 7장. 향후 계획

### 단기 (1개월)

| 항목 | 현재 | 목표 |
|------|------|------|
| FinHub 테스트 | 0% (전량 아카이브) | 주요 플로우 E2E 추가 |
| SalesHub 테스트 | 5% | Reno AI 응답 검증 추가 |
| OnboardingHub 테스트 | 4% | 온보딩 플로우 E2E 추가 |

### 중기 (3개월)

- **자동 해결 제안 고도화**: 에러가 발생하면 DB에서 유사 패턴을 찾아 "이렇게 하면 85% 확률로 해결됩니다"를 자동 제안
- **트렌드 분석**: 시간 경과에 따른 성공률 변화 차트 제공
- **배포 연동**: GitHub에 코드가 Push되면 자동으로 테스트 실행

### 장기 (6개월)

- 전체 API 커버리지 80% 이상 달성
- 전체 페이지 커버리지 60% 이상 달성
- 에러 패턴 자동 해결 (사람 개입 없이 자동 수정 후 재테스트)

### 허브별 Playwright 설정

각 허브의 `playwright.config.ts`에 Probe 리포터가 연동되어 있습니다:

```
WBHubManager/playwright.config.ts   → projectName: 'WBHubManager'
WBSalesHub/playwright.config.ts     → projectName: 'WBSalesHub'
WBFinHub/playwright.config.ts       → projectName: 'WBFinHub'
WBOnboardingHub/playwright.config.ts → projectName: 'WBOnboardingHub'
```

### 내테스터 스킬 (Claude Code 연동)

Claude Code에서 `/내테스터`를 호출하면 테스트를 자동 분류하여 실행합니다.

| 스킬 | 대상 | 속도 |
|------|------|------|
| 내테스터 | 디스패처 (자동 분류) | - |
| 내테스터-단위 | 함수, 서비스 | 5~30초 |
| 내테스터-통합 | API 엔드포인트 | 10~60초 |
| 내테스터-E2E | UI 플로우 | 1~3분 |
